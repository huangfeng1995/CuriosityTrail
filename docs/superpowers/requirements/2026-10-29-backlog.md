## 需求 1：资料员能收集的专业性内容太少

**原始诉求**：资料员能收集的专业性内容太少了，需要想想办法。

### 现状事实

| 环节 | 现状 | 位置 |
| --- | --- | --- |
| 角色提示词 | 60 行，约束的是「忠实转述 + 可溯源 + 找不到就明说」 | `web/server/services/roles/researcher.js` L26-59 |
| 站内召回 | `searchLoose(message, {limit: 4})` | `web/server/routes/ai.js` L289 |
| 联网召回 | `webSearch.search(message, {count: 4})` | `web/server/routes/ai.js` L311-315 |
| 联网抓正文 | **只抓第 1 条**，且只在作者明说「原文/全文」时才抓 | `web/server/routes/ai.js` L328-333 |
| 站内片段长度 | 160 字 | `web/server/services/search/local.js` L30 |
| 联网正文上限 | 8000 字 | `web/server/services/search/deepseekSearch.js` L45 |
| 检索词来源 | 只用作者原句，经停用词剥离后转 bigram | `web/server/services/search/local.js` L162-188 |
| 索引方式 | 应用层 bigram（中文重叠 2-gram + 单字） | `web/server/services/search/local.js` L38-56 |
| 可上传格式 | PDF / txt / md，单文件 50MB、最多 10 个 | `web/server/routes/materials.js` L31 |
| PDF 正文 | `pdf-parse` 抽取，每页插 `[[PAGE n]]` 标记 | `web/server/services/documentText.js` L48-72 |
| 扫描版 PDF | **静默不可搜**，只提示「没有可提取的文字层」 | `web/server/routes/materials.js` L191-193 |

### 问题定位

**它现在更像「带引用的摘要器」，不是能深挖的专业检索器。** 内容少不是单一环节的问题，是四个环节叠着卡：

1. **检索词不能扩写**——只用作者原句。作者问「古代炼丹用的朱砂有什么讲究」，
   库里写的是「丹砂」「辰砂」，bigram 匹配不上，专业资料就等于不存在。
2. **召回量被写死 4+4**——不管库里有 10 篇还是 100 篇相关资料，作者永远只看到 8 条。
3. **正文几乎抓不到**——联网只抓 1 条，站内只有 160 字片段。
   160 字够回答「朱砂是什么」，不够回答「怎么用、有何禁忌」。
4. **来源不分级**——只有一个 `rerankScore >= 1.5` 的阈值，没有域名白名单、没有来源分层。
   一篇论坛帖子和一篇论文在结果里长得一模一样。

### 待决策问题

- **扩检由谁做？** 规则层做同义词/别名扩展（便宜、可控，但要维护词表），
  还是模型层做查询改写（贵、灵活，但要额外一次模型调用）？
  还是让模型在多步循环里自己发起**第二轮检索**（复用 [实施计划](../plans/2026-10-29-agent-skills-plan.md) 的技能机制）？
  **第三条最值得考虑**——它把「查得更深」变成作者看得见的动作，而不是黑箱。
- **召回上限是固定 4，还是按问题类型分档？** 「朱砂是什么」要 5 条摘要，
  「写一段用朱砂的桥段」可能要 3 条但每条 2000 字。
- **来源分级要不要做？** 加白名单 / 分档是成本最低的信任建设手段：
  标出「学术 / 百科 / 论坛」比标出「相关度 0.87」对作者有用得多。
- **扫描版 PDF 要不要支持 OCR？** 现在直接静默不可搜，作者会以为是自己文件的问题。
- **专业内容从哪来？** 现状是「作者自己上传 + 联网搜通用网页」。
  是不是该有**专业语料库**（如公开的百科 / 学术摘要数据集）？
  这决定了是「把检索做深」还是「把语料做厚」——**两条路成本差一个数量级**。

### 建议下一步

先答「专业内容从哪来」这一个问题，其余三项的方案都依赖它。

## 需求 2：专注模式

**原始诉求**：需要搞个专注模式。

### 现状事实

- 三栏布局在 `web/client/src/pages/Workspace.jsx` L155-190：
  `ct-col-left` → `Resizer` → `ct-col-center`（ChapterEditor）→ `Resizer` → `ct-col-right`（AssistantSidebar）。
- `leftOpen` / `rightOpen`（`Workspace.jsx` L32-36）**只在移动端抽屉用**（L104-153），桌面端两栏常驻。
- 栏宽由 `web/client/src/hooks/useColumnWidths.js` 管（`LIMITS` L11-14、`CENTER_MIN = 420` L19、localStorage 持久化），
  `web/client/src/components/Resizer.jsx` 用 Pointer Events 拖拽、双击复位。
- 编辑器是 **textarea**，不是 contenteditable 也不是 CodeMirror（`web/client/src/components/Editor/Block.jsx` L16-18 注释）。
  块类型：paragraph / dialogue / inner / image / scene_break / setting_ref（`Block.jsx` L143-286）。
- 全局状态 `web/client/src/store/workspace.jsx` `initialState` L29-47
  —— **没有任何布局 / UI 状态字段**（无 focusMode / zenMode / panelCollapsed）。
- 样式侧 `web/client/src/styles/theme.css` L433/445/456-459 只在栏宽 <344px 时折叠角色名，**无隐藏开关**。

### 问题定位

专注模式要**从零建**，三个层次全缺：store 无状态字段、Workspace 无分支、样式无类。
好消息是栏宽基础设施（`useColumnWidths` + `Resizer`）现成，
编辑器是自研块结构而非富文本，改造面比预想小。

### 待决策问题

- **专注到什么程度？** 只隐藏 AI 侧边栏（两栏 → 一栏），
  还是同时隐藏左栏（单栏纯正文）？后者才是多数人说的「专注」。
- **进了专注模式怎么出来？** 快捷键（`Esc` / `Cmd+.`）？还是保留一个悬浮按钮？
  **必须有键盘出口**——鼠标移到屏幕边缘的操作在写作时是干扰。
- **专注时 AI 侧边栏是隐藏还是折叠成一条细边？** 折叠保留了「随时能问」，
  隐藏更彻底。作者写长段时可能想随口问一句。
- **要不要保留打字机效果 / 隐藏顶栏？** 这就牵扯到「专注」的边界定义。
- **状态存哪？** 跟 `useColumnWidths` 一样进 localStorage（跟设备走），
  还是进 store（跟账号走）？前者更符合「这是我此刻的工作台状态」。

### 建议下一步

先定「专注到什么程度」这一个问题——它决定了是改 `Workspace.jsx` 一个布局分支，
还是要动三栏的渲染结构。

## 需求 3：阅读模式分享相关结果

**原始诉求**：阅读模式分享相关结果。

### 现状事实

- **「阅读模式」这个东西还不存在。** 全项目检索 `阅读|reader|preview|share|分享`，
  命中的只是 `response.body.getReader()`、素材预览样式、版本历史弹窗、记忆片段 `ref.preview`。
- 路由表 `web/client/src/App.jsx` L161-195 只有：`/login`、`/works`、`/works/:workId`、`/materials`、`/settings`。
- 导出能力有：`web/server/routes/export.js`（347 行）
  - `GET /api/export/work/:id/{txt|markdown|docx}`、`/chapter/:id/{markdown|txt|docx}`、`/backup`、`/restore`（L6-16）
  - `blocksToParagraphs` L50-76：块 → 段落（scene_break → `---`，dialogue → 「内容」——说话人，setting_ref → 〔设定：X〕）
  - work/markdown L123-148：`# 标题` / `> 简介` / `## 大纲` / `## 章节` 结构
  - 全部走 `Content-Disposition: attachment` 下载
- 老设计文档 `docs/superpowers/specs/2026-05-12-curiosity-trail-web-design.md` L194-196 明确「分享功能（不在 MVP 范围）」。
- `web/site/` 是产品官网落地页，**不是**作品阅读页。

### 问题定位

**这是四条里唯一「从零做」的。** 缺三样东西：
1. 阅读视图（渲染层）——但块 → 段落的转换逻辑和 markdown 结构**已有现成实现**（导出模块里），可复用。
2. 公开路由 / 分享令牌的数据模型——现在完全没有。
3. 分享链接的权限语义——**这是最需要先想清楚的一件事**。

### 待决策问题

- **分享的粒度是什么？** 单章 / 整个作品 / 某个片段？
- **分享出去的东西谁能看？** 三档：
  - 私有（只有自己）——那就不叫分享
  - 持链接可看（可撤销）
  - 公开（任何人可搜到）
  中间那档最实用也最安全，**没有撤销机制的话就不要做公开**。
- **分享的是「渲染好的成品」还是「可交互的作品页」？**
  前者是静态快照（导出 HTML / PDF），
  后者是活的页面（读者能翻章节，作品还能继续更新）。
  后者体验好，但要处理「作品更新后分享链接怎么办」。
- **分享的是正文还是也带 AI 过程？** 作者可能写了 20 万字草稿，只想分享第 3 章。
  也可能整部作品都想公开，但**绝不能把 AI 引用、内部批注、草稿历史一起带出去**——
  那些是私人的，而且可能包含未完成的段落。
- **要不要脱敏？** 分享出去的 HTML 里有没有作者的账号信息、作品 id、内部链接？

### 建议下一步

先定「粒度 + 权限」两个问题，它们直接决定要不要引入公开数据模型。
若决定做「活页面」，则需要一张 `shares` 表（令牌、范围、过期时间、是否可撤销）。

## 需求 4：多用户检查 —— 存储 / token 分配要不要生成新的 key

**原始诉求**：多用户检查，比如说存储 token 分配要不要生成新的 key。

### ⚠️ 先说一个查出来的安全问题

**当前所有用户共用同一份 API key，而且任何登录用户都能改它。**

- 配置是**进程级单例**：`web/server/services/aiConfig.js` L183 `module.exports = new AIConfigManager()`，
  全模块**没有任何 userId 参数**。
- 存储位置：`DATA_DIR/ai-config.json`（`web/server/config.js` L39），**明文 key**，文件权限 0o600（L91-106）。
- 路由 `web/server/routes/config.js` L21-35：`PUT /api/ai` 直接 `aiConfig.updateConfig(cleaned)`，
  挂在 `app.js` L78 `requireAuth` 之后 —— **登录即可改全站 key**。
  限流只有 `aiLimiter` 60 次/分钟，且**全部按 IP 计数**，不区分用户（`web/server/middleware/rateLimit.js`）。
- `web/server/services/scope.js` 的归属校验清单里**没有任何 AI 配置相关函数**——AI 配置根本不走归属体系。
- 前端 `web/client/src/pages/SettingsPage.jsx` L37-44 只有 prompts / memory / backup 三个页签，**没有填 key 的入口**。
  也就是说：现在能改 key 的人，是知道接口在哪、会直接调 API 的人。

这一条与「token 分配」是同一件事的两面，建议合并处理。

### 现状事实

| 维度 | 现状 | 位置 |
| --- | --- | --- |
| 用户表 | id / phone / nickname / role / last_login_at —— **无 api_key、无配额、无用量字段** | `web/server/database.js` L52-59 |
| 唯一的按用户配置 | `prompt_overrides`，主键 `(user_id, id)` | `web/server/database.js` L253-262 |
| 字数统计 | `writing_events`，只记字数，不记 token | `web/server/database.js` L143-151 |
| provider 构造 | `constructor(settings)` —— **已经支持注入**，这是改造的关键抓手 | `web/server/services/providers/deepseek.js` L24-40 |
| provider 解析 | `resolveProvider(aiConfig)`，降级顺序 deepseek → openaiCompat → ollama | `web/server/services/providers/index.js` L44-73 |
| token 用量 | `chatStream` 返回 `{content, reasoning, finishReason}`，**不含 usage**；`chat()` 才返回 usage | `providers/deepseek.js` L110-160 / L69-105 |
| 联网搜索取 key | `deepseekSearch.js` L146+ **单独读全局** `cfg.deepseek.apiKey`，与 provider 层解耦 | `services/search/deepseekSearch.js` L146-197 |
| `getConfig()` 调用点 | 4 处，全是全局 | `routes/ai.js` L666-667 / L952-953 / L1022 / L1084 |

### 待决策问题

- **key 从哪来？** 三种模式：
  - **平台统一 key**（现状）：作者零配置，平台承担成本。**但当前是「谁都能改」，必须先堵上。**
  - **作者自带 key（BYOK）**：作者填自己的 key，平台只做代理。最省成本，但作者得自己申请。
  - **混合**：默认用平台 key（有配额），作者可填自己的 key 解除配额。**这个最可能。**
- **配额怎么算？** 按 token 还是按请求数？按 token 公平但要先有 usage——
  `chatStream` 现在**根本不返回 usage**，要改 provider 层。
  请求数简单，但一次长写作和一次「改个错别字」算一样，不公平。
- **用量记在哪？** 需要一张 `api_usage` 表（user_id、日期、token、provider、模型），
  或者 [harness 评估报告](../../research/2026-10-29-harness-evaluation.md) L373 建议的 `agent_runs` 表。
  **这两张表能不能合成一张？** 建议合成——分开会让「用量」和「运行记录」对不上账。
- **降级策略怎么定？** 作者自带 key 但余额耗尽时，是报错、
  还是回落到平台 key（作者会困惑：为什么我买的是自己的 key）？建议**报错并说清楚**。
- **免费额度给多少？** 「注册送 N 次 AI 对话」这种最常见的做法，
  但 N 定多少、要不要按天重置，都得先有计量能力。

### 建议下一步

**先堵安全口子，再谈配额。** 这两件事的顺序不能反：
在「谁都能改全站 key」的前提下讨论配额，逻辑上说不通。

分三步走：
1. **立刻**：`PUT /api/ai` 收成 admin-only（`scope.js` 已有 `isAdmin` L101，直接复用）。
   这是几行代码的事，不需要设计。
2. **短期**：加 `api_usage` 表 + 让 `chatStream` 返回 usage，为配额打地基。
3. **中期**：BYOK + 混合模式，`user_ai_configs` 表 + `scope.js` 补归属校验 +
   provider 层按用户解析 + 前端设置页加页签。

### 需求 5：编辑区水平方向太窄

**原始诉求**：编辑区太窄，浏览器页面左右两侧空着大片，正文编辑区宽度上限太小，需要让编辑区随视口宽度加宽。注意区分方向——不是「高度太短/下方留白」，而是水平方向太窄。

### 需求 6：主要编辑区两侧栏可隐藏

**原始诉求**：主要编辑两侧要可以让用户选择藏起来。

### 需求 5 + 6 联合现状与约束

| 环节 | 现状 | 位置 |
| --- | --- | --- |
| 三栏布局 | `ct-col-left` → `Resizer` → `ct-col-center` → `Resizer` → `ct-col-right` | `web/client/src/pages/Workspace.jsx` |
| 栏宽管理 | `useColumnWidths.js`，`CENTER_MIN = 420`，localStorage 持久化 | `web/client/src/hooks/useColumnWidths.js` |
| 编辑器 | textarea，块结构 paragraph/dialogue/inner/image/scene_break/setting_ref | `web/client/src/components/Editor/Block.jsx` |
| 稿纸格线 | 34px 整像素格线，行高与格线尺寸一致，块高与段距为格线整数倍 | 已修复，见项目备忘 |

**联合改造要点**：
1. 编辑区宽度上限随视口加宽，不再固定死上限
2. 侧栏支持用户选择隐藏（左栏 / 右栏各自独立）

4. 回归验证：稿纸格线对齐（34px 整像素、块高整数倍）与光标不跳底
