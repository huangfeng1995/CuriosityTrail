# 写作品质诊断：现状回顾 + 三问题根因 + 分阶段改进方案

> 日期：2026-10-31
> 性质：**只读分析**。本文不改动任何业务代码、不提交 git。
> 范围：写作生成链路、风格参照、「AI 老师」链路、AI 产出→卡片沉淀闭环、AI 交互重整、验收基线、默认档位。
> **验收口径：用户给出的范文（杨平雪地猎鹿…即刻赴许都，约两千余字）是及格线，不是参考风格。** 见 H 节。
> **质量取向：效果优先。** 默认按能达标的档位跑，成本/延迟只作为可关闭的降级项，见 I 节与决策记录。

---

## 结论先行

1. **问题 1（逻辑性不足）的第一根因不是模型能力，而是上下文装配的结构性缺口**：新章节（尤其是「第一章」）正文为空时，人物卡按「正文命中才注入」的规则一张都进不了上下文，用户指令里的人名也不参与命中判定——模型在看不到任何人物性格/动机/关系卡、只有大纲（≤4000 字截断）和设定卡的情况下一次性成稿，人物动机与因果只能靠瞎编。叠加写手提示词通篇讲「文字质感」而无一条「情节推进/因果链」要求、默认不开思考、整章塞进单个 JSON 字符串输出，「写得莫名其妙」是当前设计的必然产物而非偶发。**验收改为对准范文基线（H 节），不再用「像不像」判断。**
2. **问题 3（风格参照无效）是设计性失效**：范文原文在蒸馏后被刻意丢弃（`style/index.js:11-12`、`distill.js:7-10`），模型永远见不到样例本身，只能见到 3 项数值指标（句长/对白占比/比喻密度）+ 最多 4 条定性要点 + 禁词表。这套信息足以「避开坏毛病」，但没有任何机制让模型「按样例的写法写」——属于「注入了，但注入的不是样例，且提示词没教怎么用出样例质感」。
3. **问题 2（AI 老师加载不出）**：代码库不存在「老师」角色（五个角色：写手/编辑/审稿人/灵感师/资料员），五角色共用 `/api/ai/chat` 一条链路。最可疑的两条失败路径均有代码级证据：流式请求 60s 硬超时对思考型角色（审稿人 thinking=true + effort=high + 24k 字符上下文）偏紧；以及已复现确认的「长历史 + JSON 模式 → 返回几千个空白字符」退化，重试只保留 5 条历史。用户判断「DeepSeek API 稳定」与证据不冲突——两条路径都出在我们自己的超时与上下文策略上。

## A. 现状回顾：写作生成链路的真实数据流

### A.1 前端如何组请求

侧边栏对话（写正文的主入口），`web/client/src/components/Assistant/Sidebar.jsx:151-164`：

```js
streamPost('/api/ai/chat', {
  message, workId, chapterId, roleKey, conversationId,
  scope: 'chapter',        // 注意：恒为 chapter，从不是 work
  blocks,                  // 当前编辑中的块（可能未保存）
  useMemory, excludeRefIds, replaceMessageId,
})
```

- `roleKey` 来自顶部的角色 Tab（`RoleTabs.jsx`），默认 `writer`。
- `scope` 前端写死 `'chapter'`（Sidebar.jsx:160）——这个值直接决定人物卡/设定卡的注入策略（见 A.3）。
- SSE 事件处理在 Sidebar.jsx:165-312：`token / notice / memory / agent_thinking / tool_start / tool_done / action / done / error`。流结束但既无 `action` 也无 `error` 时，前端兜底显示「连接中断，没有收到回复，请重试。」（Sidebar.jsx:334-348）。

行内操作（选中文字改写/扩写等），`web/client/src/components/Editor/ChapterEditor.jsx:128-140` → `POST /api/ai/inline`，默认 `roleKey='editor'`，非流式。动作词表在 `web/server/routes/ai.js:1298-1306`（rewrite/expand/shorten/tone/continue/critique/colloquialize）。

### A.2 `web/server/routes/ai.js` 的动作契约

- 入参（ai.js:480-492）：`message, workId, chapterId, roleKey='writer', conversationId, scope='chapter', blocks, useMemory, excludeRefIds, replaceMessageId, retrieval`。
- 上下文装配调用（ai.js:594-603）：**只传** `workId, chapterId, roleKey, scope, retrieval, memoryRefs, blocks, userId`。**不传 `selection`、不传 `extraInstruction`**——用户的指令文本不参与人物/设定的命中判定（这是问题 1 的关键证据之一）。
- 消息数组（ai.js:687-691）：`[system(装配结果), ...trimHistory(历史,12000字), user(本次指令)]`。历史裁剪见 `context.js:110-127`，超预算只留最近段且强制从 user 边界开始，省略条数追加写进 system（ai.js:695-697）。
- 输出契约：模型必须输出单个 JSON `{action, target, content, reason, citations}`（writer.js:103-119）；合法 action 为 `replace/append/insert/comment/none/call_tool`（ai.js:78）。`call_tool` 进入多步循环（`services/agent/loop.js`，上限 4 步，loop.js:21），工具结果截断到 4000 字回灌（loop.js:24,35-43）。
- 空回复处理：一轮返回全空（无 raw、无 parsed、无流式 token）时自动重试一次，重试只保留最近 5 条消息并在末尾追加提醒（ai.js:808-850，`RETRY_HISTORY_KEEP=5` 在 ai.js:1139）。代码注释记录了复现结论：「完整历史 + JSON 模式 → 稳定返回两三千个空格和换行」（ai.js:826-831）。重试仍空则报错并清理孤立消息（ai.js:901-972）。
- JSON 解析失败的退路：模型没给 JSON 但给了文本 → 整段降级为 `comment`（ai.js:877-880），**不可应用到正文**。

### A.4 角色提示词对输出的约束（`web/server/services/roles/`）

写手（writer.js）——与问题 1 直接相关，逐项核对「用户标准」：

| 用户标准（好稿子该有的） | 写手提示词里有没有 |
|---|---|
| 情节推进清楚、每段都推进或铺垫、不空转 | **没有**。全文无任何「推进/铺垫/节拍/因果」字样；「四层自检」是人物逻辑/情绪节奏/文字质感/真实感（writer.js:84-90），无情节维度 |
| 人物动机与关系交代完整 | 有原则 1「人物先行」（writer.js:45），但**约束的是「不 OOC」而非「必须交代动机与关系」**；且人物卡在空章节根本不在上下文里（见 A.3 第 3 层） |
| 历史/地理/行政细节自洽 | **没有**。无一条要求核对年号、官职、地理；只有宽泛的「真实感」自检（writer.js:88） |
| 环境描写服务叙事 | 有（writer.js:49「环境自带情绪」） |
| 结尾留悬念 | 有（writer.js:52「结尾留余味」） |
| 篇幅/结构 | **没有**。无字数要求、无场景划分要求、无开头规划要求；只有「一口气写完。不先讲思路、不列提纲」（writer.js:42）——**明确禁止先规划** |

其他角色：编辑（editor.js，温度 0.6）、审稿人（critic.js:18-20，`model='deepseek-v4-pro'`、`thinking=true`、温度 0.4——全角色唯一默认开思考）、灵感师（inspiler.js，0.95）、资料员（researcher.js，0.3）。提示词可被用户按角色覆盖，存 `prompt_overrides` 表（roles/index.js:31-48），但**角色名不可覆盖**（withOverride 只覆盖 prompt/temperature/model/thinking，roles/index.js:63-79）。

### A.5 模型参数（实际生效值）

- Provider 解析：`resolveProvider`（providers/index.js:44-73），DeepSeek 未配 key 时静默降级 Ollama（降级会发 notice，ai.js:702-704）。
- 聊天路径 `runAgentLoop` 的 options（ai.js:755-761）：`temperature = role.temperature`（写手 0.85）；`model` 仅当 provider 是 deepseek 时才用角色模型；`thinking` 角色没配就跟随全局，**全局默认关闭**（aiConfig.js:29）；**不传 `maxTokens`**。
- `max_tokens`：取 provider 配置，`settings.maxTokens ?? 4096`（deepseek.js:28,48）；aiConfig 默认 8192（aiConfig.js:24）。**思考模式下 reasoning 计入 max_tokens**（deepseek.js:48 注释与 ai.js:178-180 的截断报错分支）。
- 温度只在非思考模式下发（deepseek.js:53-60）：思考模式下官方忽略采样参数。
- 流式 + `stream_options.include_usage`（deepseek.js:66-70）；`response_format=json_object`（deepseek.js:62-64，chat 与 inline 都开）。
- 超时：单次 fetch 60s（base.js:118，`fetchWithRetry` 对整条流生效，base.js:151-196）；整轮 120s（ai.js:512）。

### A.6 「第一章」场景下，模型实际能看到什么（实测推演）

以「新建空白第一章 + 侧边栏让写手写开头」为例，system 消息依序为：

1. 写手提示词全文（约 2800 字，讲文字质感与 JSON 契约）；
2. 文风要求（若配了卡，见 B 节）；
3. 作品信息：标题/题材/简介/大纲（大纲 >4000 字部分被截）；
4. 当前章节：标题/卷/状态；
5. **人物层：大概率是空的**——`collectMatchText`（context.js:282-297）只收集章节标题+正文+块内容+对白说话人，空章节下 ≈ 只有章节标题；`selectCharacters` 按名字/别名命中过滤（context.js:184-190），标题里没有的人一张卡都进不来。**用户指令里写了人名也不救**——指令不参与命中（A.2）；
6. 设定层：importance≥3 的全量（年号、地理、官职若作者建了卡且标了高重要性，能看到）；
7. 「本章还没有正文」指引；
8. 技能清单（check_style / check_consistency / audit_foreshadowing 的调用说明）；
9. （可能有）长期记忆召回若干条——记忆层确实索引了人物卡/设定卡，阈值按类型分档（retriever.js:59-78,127,418），指令提到人名时有机会召回，但受阈值与条数限制，是「可能补偿」而非「保证注入」。

**一句话：第一章的写手是在「看不到人物卡、看不到完整大纲（若超 4000 字）、没有写作规划、被禁止列提纲、一次性输出整章 JSON」的条件下动笔的。**

> 证据缺口：账号 `18210200254` 的第一章实际产出与当时的上下文快照无法本地验证——本机 `web/data/curiosity.db` 只有一张空的 `works` 表（开发库），生产库在香港服务器。验证方式（只读）：
> `sqlite3 <生产库> "SELECT c.title, c.word_count, substr(c.content,1,200) FROM chapters c JOIN works w ON w.id=c.work_id JOIN users u ON u.id=w.user_id WHERE u.phone='18210200254' ORDER BY c.seq LIMIT 3;"`

## B. 风格参照的真相

### 数据流（现状全链路）

1. **配置入口**：`POST /api/style/cards`（routes/style.js:55-138），样例可以是粘贴文本或作者自己的章节；分 good/bad 两类；可挂作品级或全局。
2. **蒸馏**：`services/style/distill.js`。样例截 4000 字（distill.js:22）→ 本地算 3 项指标（metrics.js）→ 调模型（temperature 0.2、thinking 关闭、maxTokens 1200，distill.js:117-128）产出规则 JSON：`summary + metrics{句长/对白占比/比喻密度} + bannedWords + notes(≤4 条)`（distill.js:70-91）。蒸馏提示词**明确禁止输出原文具体词句**（distill.js:57）。
3. **存储**：`style_cards` 表只存规则 + ≤100 字摘要（`EXCERPT_LIMIT`，style/index.js:18-19）；**原文调完模型即丢，绝不落库**（style/index.js:11-12；routes/style.js:12-14 注释）。这是刻意的设计决策（防负样例污染、省预算），记录在 `docs/superpowers/plans/2026-10-30-style-reference-plan.md`。
4. **生效解析**：作品级整类替换全局级（style/index.js:167-200）；多卡合并，数值取交集、词表取并集（rules.js:111-168）。
5. **注入**：`getStylePrompt`（style/index.js:209-212）→ `assembleContext` 里作为 **fixed** 分区注入（context.js:347,359-361）——不会被 24000 预算裁掉。措辞（rules.js:210-215）：

   > ## 文风要求
   > 以下是作者明确设定的文风标准，优先于你的默认文风。写正文时必须遵守。
   > ### 要学的（作者欣赏的文风）
   > 整体感觉：{summary}
   > 句长在 X–Y 字/句之间；对白占比在 A–B% 之间；比喻密度不超过 N 处/千字
   > 这些词不要出现：…
   > 要点：…（≤4 条拼接）

6. **生效范围**：所有 action——`/chat` 与 `/inline` 都走 `assembleContext`，风格段都会注入；不分续写/改写/起稿。
7. **事后核对**：技能 `check_style`（skills/checkStyle.js）只核 3 项数值 + 禁词（checkStyle.js:7-14），且只在模型自己决定调用时才执行，定性 notes 不核。

### 「配了没效果」属于哪一类

四类排查：没注入 / 注入了被截断 / 注入了但提示词没教怎么用 / 用上了但被参数淹没。

- 「没注入」：**大概率排除**。fixed 分区保证注入（context.js:359-361,69-72）；但有一个**待验证假设**：用户那张卡是否 `enabled=1`、作品级/全局归属是否匹配当前 workId（生产库不可本地查）。验证：`GET /api/style/cards?workId=<id>` 返回里每卡有 `effective` 布尔（routes/style.js:36-43）。
- 「注入了但被截断」：**排除**。fixed 分区不参与截断。
- **「注入了，但注入的不是样例，提示词也没教怎么用出样例」——主根因**。模型看到的是「句长 20–35 字」这类抽象约束，而不是范文的章法、节奏、叙事密度与视角处理。蒸馏的信息保真度上限就是 3 个数 + 4 句话；且蒸馏时明确禁止保留原文词句（distill.js:57），连「像谁」的锚点都没留下。
- 「用上了但被参数淹没」：**部分成立**。写手温度 0.85 偏高，且写手自带一套很强的「白描」先验（writer.js:9-12,36-52）；注入措辞虽写了「优先于你的默认文风」（rules.js:212），但在没有样例可锚定的情况下，模型遇到冲突时只会退回自己最熟的写法。

**结论：风格参照当前是「负面清单 + 三项数字护栏」，不是「样例模仿」。对「去掉 AI 腔」这种质感目标，机制上就不具备生效条件。**

## C. 「AI 老师」定位与失败路径

### C.1 「老师」到底是谁

- 角色注册表只有五项：`writer/editor/critic/inspiler/researcher`（roles/index.js:16-22）；全仓库 grep `老师|teacher` **零命中**（已验证，含前后端与文档）。
- 角色显示名不可被用户覆盖（roles/index.js:63-79），所以也不存在用户改名出的「老师」。
- 结论（标注**假设**，需用户确认）：「AI 老师」是用户对某个指点型角色的称呼——最可能是**编辑**或**审稿人**，或对整个侧边栏 AI 对话的统称。五角色共用 `POST /api/ai/chat`，下列失败路径对所有角色同样成立；其中审稿人（thinking=true）命中路径 1 的概率最高。

### C.2 失败路径清单（每条带最小验证方法）

| # | 路径 | 代码位置 | 最小验证方法 |
|---|------|----------|--------------|
| 1 | **流式 60s 硬超时**：`fetchWithRetry` 给整条流挂 `AbortSignal.timeout(60000)`；思考型角色在 24k 字符上下文上思考极易超 60s，abort 后报「AI 请求超时（60 秒未完成）」 | base.js:118,151-196；critic.js:18-20 | 服务器日志：`docker logs <容器> 2>&1 \| grep 'AI 请求超时'`；或复现：对长章节用审稿人提问，秒表计时 ≈60s 出错误 |
| 2 | **整轮 120s 上限**：多步循环或慢流触顶，报「AI 这次没能及时返回（请求超时）」 | ai.js:512,1045-1049 | 日志 `grep '"event":"ai_chat"'` 看 `durationMs` 是否 ≈120000（ai.js:854-870） |

## 补充专题：AI 产出 → 卡片沉淀闭环

### E0.1 现状

- 人物卡、设定卡、情节卡**全部手工维护**：用户在对应页面逐张新建（routes/characters.js、settings.js、plotCards.js）。AI 写完一段正文后，系统不做任何「这段引入了新人物/新设定/新伏笔」的识别。
- `applyPlan.js`（前端，308 行）只负责把 AI 的结构化输出写回正文块，写回即结束，无任何后续环节。
- 唯一的自动抽取在长期记忆里：每轮对话后异步抽「事实层」（conv_fact），供召回用（memory/extractor.js、conversation.js:94）——它抽的是「作者与 AI 说过什么」，不是「故事里存在什么」，产出不进人物/设定/情节卡。
- 数据模型（database.js:127-184）：
  - `characters`：`name` 自由文本、`aliases` 逗号分隔串、无外键唯一约束，`idx_characters_work` 只是普通索引（database.js:155-171）。
  - `settings`：`category+name`，同样无唯一约束（database.js:174-184）。
  - `plot_cards`：`title/kind/status`，可挂 chapter（database.js:127-140）。
  - **同名、别名、跨章节重复：数据库层完全不拦，应用层也不查**（characters.js grep 无重名校验）。重名卡目前只能靠作者自己发现并手删；上下文装配按名字子串命中（context.js:159-175），重名卡会被重复注入。
- 上下文消费侧已有现成闭环的「回流端」：卡片一旦存在，就会经 FACT 层注入（A.3 第 3/4 层）——缺的是「沉淀端」。

### E0.2 联动链路设计

```
生成正文 → 作者点「应用到正文」(applyPlan 成功)
        → 服务端异步识别：这段正文里值得沉淀的实体/情节
        → 写入 card_proposals（pending）
        → 前端在已应用的消息上弹出「发现 N 个可沉淀的卡片」提案条
        → 作者逐条：确认（可改）/ 驳回 / 忽略
        → 确认 → 走现有 CRUD 落库（新建或合并进已有卡）
        → 下一轮生成经 FACT 层自动注入 → 约束生效 → 闭环
```

关键决策点：

1. **识别在哪一层做：服务端，异步二次识别**。复用 `memory/extractor.js` 的成熟模式（temperature 0.2、小 maxTokens、失败静默、绝不阻塞主链路）。**不选「生成同轮让模型多输出 entities 字段」**：那会加重 JSON 契约、挤占正文 token、提高空回复率（问题 1 的 R6 已经够糟）。
2. **触发时机：作者点「应用到正文」成功之后**，而非生成后立即。理由：只有落地的正文才是故事事实；生成后立刻提案会把作者没采用的稿子也沉淀进去，污染卡片库。行内改写（/inline）同理，写回后触发。未应用的提案不创建。
3. **避免重复的合并规则**：
   - 服务端按 `work_id + 标准化名称`（去空白/大小写/全半角）+ `nameVariants` 同款别名表查重；
   - 命中已有卡 → 提案类型为「**补充**」：建议把新信息合并进指定字段（如 personality/goal/notes），作者确认后走 update，不新建；
   - 未命中 → 「**新建**」提案，预填识别出的字段；
   - 跨章节重复天然由 work_id 作用域消解；DB 层建议后续加 `(work_id, 标准化name)` 唯一索引兜底（存量先查重再建索引，属迁移动作）。
4. **驳回后不再打扰**：新增 `card_proposals` 表记录 `(work_id, kind, normalized_name, status, source_message_id, payload, created_at)`；`status=rejected` 的同 fingerprint 实体不再生成提案；「忽略」（超时未处理）不等于驳回，下次仍可出现，但同一段正文不重复提案（按 source_message_id 去重）。
5. **哪些不该提案**（降噪红线）：
   - 只出现一次、无对白、无动机描写的路人（店小二、传令兵）；
   - 泛化名词（「京城」「一把剑」这类无特指限定词的）；
   - 仅在叙述中被提及但未展开的地名/组织；
   - 建议准入：出场 ≥2 次，或有对白，或有动机/关系描写，或作者在用词上给了专名+限定（「司空府的符传」）。
6. **识别提示词要点**：输入为「刚应用的正文段 + 已有卡名单（名称+别名）」，输出仅为提案 JSON 数组，每条带 `kind(character/setting/plot)、name、建议字段、依据原文句、置信度`；模型只做提取不做创作，置信度低的不返回。

### E0.3 与问题 1 的关系（为什么它属于阶段一）

卡片是**长期约束的载体**。没有沉淀端，「故事里有什么」只能活在两处：作者脑子 + 每次对话的零散上下文（12000 字正文 + 4000 字大纲 + 运气好的记忆召回）。这正中问题 1 的 R1/R2：第一章写完的人物，第二章生成时若正文没提到名字，连已有的卡都进不了上下文；没建卡的就彻底消失。前后不一致、人物行为莫名其妙，相当一部分是「约束没有家」的直接后果。闭环把「写过即沉淀、沉淀即注入」变成默认路径，是从根上改善一致性的杠杆，因此列为**阶段一的组成部分**（与提示词契约修正并列，而非后置优化）。

### E0.4 失败与降级

- 识别服务失败/超时/输出非法 JSON：**静默**，正文应用早已完成，无任何用户可见影响；日志记 `card_propose_failed`。
- 模型误判：作者驳回即终态，fingerprint 防再扰；误判成本 = 一次点击。
- 用户不确认：提案停留在消息气泡上，不阻塞任何后续操作；正文早已落库。
- 提案接口本身失败：toast 提示「提案生成失败，不影响正文」，正文不回滚。
- 与记忆抽取共用 provider 时相互独立：任一失败不影响另一。

## F. 需要用户拍板的问题（按重要性排序）

1. **范文原文是否允许入库**：I.1 已把「范文锚点」设为默认必注入，但这需要破例现行「原文绝不落库」原则（style/index.js:11-12 是刻意决策）。是否允许「用户逐卡显式授权、单卡 ≤1500 字锚点片段」？——这是默认效果档能否成立的前置条件。
2. ~~写手质量路线~~ **已定（2026-10-31 效果优先）**：默认 L0（强模型 + 思考 + 规划 + 全上下文 + 范文锚点），按 I.1 / I.2 执行，不再作为待选项。
3. **卡片提案的触发时机**：推荐「应用正文后异步识别」（打扰最少、只沉淀落地稿）；备选「生成完成即提案」（沉淀率高但会提案废稿）或「手动盘点按钮」（最克制但依赖作者记得点）。
4. **「AI 老师」到底指哪个入口**：请确认是编辑、审稿人，还是侧边栏整体。修复本身覆盖全角色共用链路，但定位用户实际命中的失败路径（C.2 表）需要这个信息 + 一次服务器日志核查授权。
5. ~~正文输出契约是否去 JSON 化~~ **已定（按此前结论不变）**：阶段一只加「作为正文应用」的退路（1.4），阶段二再评估纯文本协议；不改 writer 契约。

## G. AI 交互重整（用户 2026-10-31 补充）

> 用户原话：「审稿人给出了意见，应该在文章对应的部分显示。现在单独在右侧显示，我都不知道哪部分有问题。还有就是给出结论后应该能很丝滑地让用户确认后让写手去修改。顺着我这个思路过一遍 AI 交互这些设计和功能，现在用起来不方便。」

### G.1 现状盘点

**意见与正文之间没有任何锚定**。审稿人/编辑的产出（`action='comment'`）就是一段纯文本：没有块 id、没有文本 range、没有行号、没有 quote 字段——消息落库结构只有 `{action, target, content, reason, citations}`（ai.js:73-127），`comment` 语义下 `target` 无约束。citations 只指向外部素材/记忆来源，不指向正文位置。作者看到「第三章第二段逻辑有问题」，要自己用眼睛去找。

**ActionCard 的五种 action 前端呈现**（ActionCard.jsx:5-49）：

| action | 标签 | 呈现 |
|--------|------|------|
| replace/append/insert | 改写/续写/插入 | 右侧卡片 + 「应用到正文」按钮，点完变「已写入 + 撤销」 |
| comment/none | 建议/回复 | **只是右侧气泡里的静态文字，无任何可点动作**——审稿意见全在这里，看完即死 |

**应用正文**：`planApply`（applyPlan.js）按 target 是块 ID 还是原文片段定位，四种落笔方式 replace/append/insert/error；片段 <6 字且多处命中时拒绝（歧义保护，applyPlan.js:20-28）。

**撤销**：双轨且互不知晓——(1) 消息级快照撤销（Sidebar.jsx:401-446），只退回该消息改动的那一个块，多块改动无法整笔撤销；(2) 全局 undo/redo 栈（workspace.jsx:277-348），`updateBlock/insertBlock/removeBlock` 都会 `pushHistory`，所以 AI 回写**会**混进全局撤销栈，与作者手打的编辑叠在一起——按 Ctrl+Z 会先撤销到 AI 写的还是手写的，全凭时序，没有分组。

**审稿→修改的通路**：目前为零。审稿人给完意见后，想让写手照改，只能作者自己把意见复制粘贴成新指令发给写手（这正是此前已报的「重写链路」bug 场景）。系统层面不存在「意见 → 改写任务」的传递。

### G.2 五个真实剧本（按使用场景组织，不按功能点）

每个剧本四段式：**此刻想干什么 → 现在要经过哪些步骤 → 摩擦点 → 重设计后几步完成**。

#### 剧本 1：新建一章，从零起稿

- **此刻想干什么**：脑子里有一个开场（雪地猎鹿 → 失手 → 同伴嗔怪 → 回城 → 父亲突至 → 司空征辟 → 即刻赴许都），想让它变成两千余字的正文，且达到范文的水准。
- **现在要经过的步骤**：① 新建章节 → ② 打开右侧栏 → ③ 手动切到写手 → ④ 把人物性格、关系、年号、官职、地理、结构全部写进一条长指令（因为空章人物卡不进上下文，见 A.6）→ ⑤ 等流式 → ⑥ 产出无规划、流水账、动机缺失 → ⑦ 点「应用到正文」整段覆盖（无 diff）→ ⑧ 不满意，重新生成或手动改 → ⑨ 下一章重复第 ④ 步（因为什么都没沉淀）。
- **摩擦点**：指令在替卡片干活；没有规划步；整段覆盖无预览；产出不沉淀。
- **重设计后 6 步**：① 新建章节（自动注入全量人物卡/设定卡/大纲，见 1.1）→ ② 输入一句选题 → ③ 系统先出 ≤5 节节拍规划（可改、可跳过）→ ④ 确认，正文流式 → ⑤ diff 预览 → ⑥ 应用 → ⑦ 卡片提案条一键确认沉淀（E0.2）。**0 次复制粘贴。**

#### 剧本 2：已有初稿，让写手按审稿意见改

- **此刻想干什么**：初稿写完了但「读着不对」，想让审稿人挑毛病，再让写手照着改。
- **现在要经过的步骤**：① 右侧切审稿人 → ② 提问 → ③ 右侧给一大段评语 → ④ 作者自己在正文里找「它说的是哪一段」→ ⑤ 复制该条意见 → ⑥ 切回写手 → ⑦ 粘贴 + 补充「改哪段、改成什么样」→ ⑧ 等产出 → ⑨ 肉眼对照新旧 → ⑩ 应用。
- **摩擦点**：意见没有锚点（不知指哪）；跨角色无传递（复制粘贴是唯一通路）；无 diff；撤销粒度混乱。
- **重设计后 7 步**：① 切审稿人 → ② 一键审稿 → ③ 意见以边注落在正文对应段落（锚点批注，见 G.3）→ ④ 勾选 5 条 → ⑤ 「采纳并让写手改」（批量）→ ⑥ diff 确认（逐条/整批）→ ⑦ 应用 + 一次原子撤销。**0 次复制粘贴。**

#### 剧本 3：写到一半，需要查前文 / 设定（「AI 老师」的典型入口）

- **此刻想干什么**：「上一章司马防是不是已经提过征辟？温县到许都多少里？」希望就地得到答案，不打断写作。
- **现在要经过的步骤**：① 右侧提问 → ② 可能等 60s 后超时或收到「模型没有返回内容」→ ③ 放弃，自己去章节列表翻 → ④ 找不到就靠记忆。
- **摩擦点**：失败不可诊断（超时/空回复/降级混成一句话）；答案悬在右侧，无法回跳原文核对。
- **重设计后 3 步**：① 选中疑难句 → 「问 AI」→ ② 答案带来源（章节/人物卡/记忆条目）且每条可「跳到原文」→ ③ 失败时错误条给出具体原因（超时/空响应/降档）与「重试」。**0 次翻列表。**

#### 剧本 4：一章写完，沉淀与下一章准备

- **此刻想干什么**：这一章新出现了两个人物、一条设定、一个伏笔，想在开始下一章前把它们记下来。
- **现在要经过的步骤**：① 自己回想本章新增了什么 → ② 去人物页逐张新建 → ③ 去设定页新建 → ④ 去情节卡页新建 → ⑤ 下一章生成时若正文没提到名字，这些卡还是进不了上下文（R1）。
- **摩擦点**：纯手工、易漏；建了卡也可能不生效。
- **重设计后 3 步**：① 章末「本章沉淀」一键盘点 → ② 提案列表批量确认（可改字段、可驳回）→ ③ 进入下一章，卡片已作为上下文约束注入（E0.2 闭环 + 1.1 兜底）。

#### 剧本 5：不同意某条意见

- **此刻想干什么**：审稿人说「这一段节奏拖沓」，但作者就是想要这个慢镜头。希望它别再出现。
- **现在要经过的步骤**：无机制——意见留在对话流里，下次重新审稿再来一遍，作者只能自己记住忽略。
- **摩擦点**：驳回不可表达、不可持久。
- **重设计后 2 步**：① 点「不同意」（可选一句理由）→ ② 同 fingerprint 的意见不再出现；主动重新生成审稿意见时重置。

### G.4 端到端验收（点击次数上限 + 禁止复制粘贴）

| 剧本 | 端到端路径 | 点击次数上限 | 硬约束 |
|------|------------|--------------|--------|
| 1 起稿 | 新建章 → 一句选题 → 规划确认 → 应用 → 沉淀确认 | ≤8 次 | 全程无复制粘贴；应用前必须出现 diff |
| 2 审稿改稿 | 切审稿 → 审稿 → 勾 5 条 → 采纳 → 确认 diff → 应用 → 撤销 | ≤10 次（含撤销） | 5 条意见全部正文可定位；0 次复制粘贴；一次 Ctrl+Z 整批退回 |
| 3 查前文 | 选中句 → 问 AI → 跳原文 → 返回 | ≤4 次 | 答案 100% 带来源；失败时给出可执行原因 |
| 4 章末沉淀 | 章末盘点 → 批量确认 | ≤3 次 | 确认后的卡下一章必进 `meta.characters`；驳回项不再出现 |
| 5 驳回 | 不同意 → 刷新 | ≤2 次 | 同 fingerprint 不再出现；重新生成审稿时重置 |

统计口径：点击 = 一次鼠标点击或一次快捷键；「输入选题」不计点击但计一次输入；「切换角色」若被自动化（默认写手/一键审稿）不计入。

### G.5 优先级映射到剧本

**P0（不改就没法用）**

| # | 项 | 落在哪个剧本 | 验收 |
|---|----|--------------|------|
| P0-1 | 意见锚点化 | 剧本 2、5 | 给定 5 条审稿意见，5 条都能定位到正文段落；点任一边注右侧滚到该条，反之亦然；未定位条目显式标注且可手动指认 |
| P0-2 | 采纳闭环（单条/批量） | 剧本 2 | 两次点击（选批注→确认 diff）完成一次采纳；5 条批量采纳后一次 Ctrl+Z 整笔退回；驳回条目刷新后不再出现 |
| P0-3 | 应用前 diff 预览 | 剧本 1、2 | 任意 AI 产出点「应用」必先见 diff，确认才写 |

**P1（顺手的优化）**

| # | 项 | 落在哪个剧本 | 验收 |
|---|----|--------------|------|
| P1-1 | 错误条独立化 + 空响应动作条 | 剧本 3 | 注入空响应，提问上下文保留，错误条给「重试」，点击后原样重发成功 |
| P1-2 | 消息级撤销与全局栈分组互通 | 剧本 2 | AI 回写后 Ctrl+Z 一步退回，不穿插撤销到更早的手写编辑 |
| P1-3 | 正文内人物/设定名悬浮卡摘要 | 剧本 4 | 有卡人物 hover 显示摘要，无卡提示「未建卡」 |
| P1-4 | 规划步折叠展示与可改 | 剧本 1 | 规划默认展示，可编辑/跳过，跳过时记录一次「直写」日志 |

P0 三项直接回应用户两条原话（意见落不到正文、采纳不顺滑）；P1 是同一思路的延伸打磨。P0-1/P0-2 依赖输出契约扩展（findings 带 quote），与 F-5「输出契约去 JSON 化」可合并设计，但**不互相阻塞**：findings 可先在现有 JSON 契约内扩展字段落地。

### G.6 与既有根因的关系

- 本节不改模型质量本身，但它拆掉的是「意见 → 修改」的人工搬运摩擦——此前「手动复制同一内容给写手能正常重写」的案例说明链路的每一步单独都通，断的是连接处。采纳闭环把这个连接变成产品的一等公民。
- 锚点批注的 `quote + locateSnippet` 定位机制与伏笔盘点「未能定位到原文」的既有处理同构，复用同一套降级语义，不引入新的失败模式。

> 用户已两次原样贴出范文（杨平雪地猎鹿、故意失手、司马懿嗔怪、回城、父亲杨俊突至、司空征辟、即刻赴许都，约两千余字）。**它是验收基线，不是参考风格**——达不到即不合格。

### H.0 基线来源与证据等级

全文未在本仓库/附件/记忆中留存（已检索确认），因此本文数字分三级标注，范文文本回填后由 H.4 脚本重算并替换：

| 等级 | 含义 | 当前状态 |
|------|------|----------|
| S | 对范文原文直接实测 | **待回填**（需把范文存为 `docs/superpowers/baseline/sample.md`） |

### H.2 可测验收项（阶段一以此为准）

分三组：**A 结构**（打分可客观化）、**B 内容质量**（事实与动机可判定）、**C 文风代理**（数值）。

| B4 | 跨章一致性 | 与已有章节/人物卡/设定卡比对 | 冲突数 **= 0** | 人工 |
| B5 | 时空可追踪 | 时间线无倒退、场景跳转有交代 | 违规 **= 0** | 人工 |
| B6 | 章末钩子 | 能否用一句话概括未解悬念 | ≥1，且非「且听下回分解」式空钩 | 人工 |
| C1 | 对白占比 | `measureDialogueRatio` | 25%–35% | 脚本 |
| C2 | 比喻密度 | `measureImageryDensity` | ≤ 基线值（待 S 回填） | 脚本 |

**合格判定**：A1–A5、B1–B6 全部达成，且 C1–C3 全部达成，视为「达到基线」。任一 A/B 项不达标即整体不合格（不取平均分）。

### H.3 这套验收怎么做

**样本与并排**

- 同题 3 次生成（temperature 固定 0.85，同上下文配置），编号 S1/S2/S3；
- 基线 B0 与 S1–S3 **同屏并排**，按随机顺序呈现，四份都不标来源（真正盲评）；
- 每份按 H.2 表逐项填，先填客观项（A4/A5/C1/C2/C3 由脚本先出），再填人工项。

**谁打分**

- 3 名评审：作者本人 + 2 名非项目成员（避免「自己写的自己满意」）；
- 人工项双人独立标注，一致性用 Cohen's κ 衡量，**κ ≥ 0.6** 才认可该轮结论；分歧项由第三人仲裁；
- 评审只看到文本 + H.2 打分表，不看到「哪份是 AI、哪份是基线」。

**达不到时如何定位到具体缺口**（四环归因）

| 观察到的症状 | 归因环 | 下一步改哪里 |
|--------------|--------|--------------|
| 空转多、节拍散、无因果 | 规划步 / 提示词契约 | 改规划步拆解粒度、补「每段必须推进或铺垫」硬约束（1.2） |
| 文笔尚可但人物动机缺失、关系不清、史实外行 | 上下文注入 | 补人物卡/设定卡注入（1.1）、补前文章节摘要、复查大纲截断 |
| 结构事实都对，但读起来仍「AI 腔」 | 模型选择 / 风格层 | 升档（思考 + pro，见 I.2）、注入范文锚点（2.1） |
| 输出被截断、JSON 坏、正文丢失 | 输出协议 | 阶段一用「作为正文应用」退路（1.4）；阶段二评估纯文本协议（F-5） |

**迭代闭环**：每一轮只改**命中的那一环**，改完重跑同一流程；记录表见 I.3。连续 2 轮 A/B 全达标且 C 全达标才可宣布阶段一完成。

## I. 默认档位与降级链（效果优先）

> 用户取向：「达不到想要的结果就想办法达到就行。」→ **默认按效果档跑，成本与延迟只作为可关闭的降级选项，不作为削弱默认方案的理由。**

### I.1 默认档位表

| 环节 | 默认档位 | 具体值 | 是否可降 |
|------|----------|--------|----------|
| 规划步 | **必开** | 先输出 ≤5 节节拍（事件/人物动机/时空），确认或超时 3s 自动继续 | 仅「极速模式」可关 |
| 模型 | **强模型** | 起稿/续写/审稿：`deepseek-v4-pro`（不用 flash） | 可降 L2/L3 |
| 思考 | **起稿开启** | `thinking=enabled`，`reasoning_effort=high` | 可降 L1 |
| 温度 | 思考开启时不生效（官方限制）；关闭时 0.85 | 记录在消息元信息里，避免作者误以为调温有效 | — |
| 上下文 | **必注入** | 空章/前 3 章：人物卡全量；设定卡 importance≥3 全量；大纲全文（按预算优先，不再 4000 字硬截）；前情摘要 + 最近 1500 字尾 | 可降（额度受限时） |
| 范文锚点 | **必注入** | good 卡 ≤1500 字锚点片段（需作者一次性授权，见 F-1）+ 蒸馏规则 | 可降 |
| 输出协议 | 阶段一维持 JSON + 「作为正文应用」退路 | 与 F-5 一致：阶段二再评估纯文本协议 | — |
| max_tokens | **按正文长度反推** | 2500 字正文 ≈ 3000–3500 tokens + JSON 转义余量 20% → 设 6000；思考预算单列（不占正文额度） | — |

### I.2 降级链

| 档位 | 组合 | 触发条件（自动） | 产出标记 |
|------|------|------------------|----------|
| **L0**（默认） | 强模型 + 思考 + 规划 + 全上下文 + 范文锚点 | 默认，无条件 | 无标记 |
| L1 | 强模型 + 规划（关思考） | 首字节 >60s 或总时长触顶 180s 出现 2 次；或思考导致 `finish_reason=length` 且正文为空 1 次 | 「降档：已关闭深度思考」 |
| L2 | 快模型 + 规划 | 强模型连续 2 次失败（超时/空响应/5xx 重试耗尽）；或额度不足返回 402/429 | 「降档：已切换快模型」 |
| L3 | 快模型直写（无规划） | L2 仍连续 2 次失败；或作者手动选「极速」 | 「降档：极速模式（无规划）」 |

规则：

- **降档只自动发生一次，不连锁试探**：同一轮内最多降一档，避免一次故障把质量连降三级；
- **降档必须可见**：消息上打徽标 + 一句人话原因 + 「用效果档重试」按钮；日志记 `tier` 字段；
- **不自动回升级**：本轮结束后不自动重试高档次，由作者点按钮或下一轮重置为 L0；
- 额度恢复后下一轮自动回 L0（每轮独立判定）。

### I.3 迭代机制：「达不到就继续想办法」

不是一次性验收，是可重复的评测循环：

1. **跑一轮**：基线 B0 + 同题 3 样本，盲评（H.3）；
2. **记差值**：逐项记录 A/B/C 与基线的差距，形成本轮差距表；
3. **归因**：按 H.3 四环表定位到唯一主因环（规划 / 上下文 / 提示词+模型档 / 输出协议）；
4. **只改那一环**，不改其它环（避免多变量同时变导致无法归因）；
5. **重跑同一流程**，对比上一轮差距表；
6. **停止条件**：连续 2 轮 A/B 全达标且 C 全达标；或作者判定「够用」。

轮次记录表（每轮一行，落 `docs/superpowers/baseline/rounds.md`）：

| 轮次 | 改动环 | A1 | A2 | B1 | B3 | C1 | 是否达标 |
|------|--------|----|----|----|----|----|----------|

**这一条本身就是交付物**：没有轮次记录，不能宣称「写手已经达标」。

### I.4 成本与延迟量级（仅作记录，不用于降默认档）

以单章 2500 字估算：

| 档位 | 输入 token | 输出 token | 耗时 | 相对成本 |
|------|-----------|-----------|------|----------|
| L0 | 12k–20k（24k 字符上下文 + 卡片 + 锚点） | 5k–9k（规划 + 思考 2–5k + 正文） | 80–160s | 1×（基准） |
| L1 | 12k–20k | 3k–4k | 50–90s | ≈0.6× |
| L2 | 12k–20k | 3k–4k | 35–60s | ≈0.3× |
| L3 | 10k–16k | 2.5k–3.5k | 25–45s | ≈0.2× |

结论：**默认 L0**。成本只在「额度受限」或「作者主动选极速」时下降；不得因成本把默认档调低。
